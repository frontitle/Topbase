# 性能与容量

Topbase 把低内存占用、快速页面加载和持续稳定运行作为发布质量指标。性能优化必须通过可重复测试验证，不能以单次主观体验代替容量规划。

## 默认保护

| 项目 | 默认值 | 作用 |
| --- | --- | --- |
| Docker 容器内存 | 512 MB | 防止单个 Topbase 节点耗尽宿主机内存 |
| Docker Go 托管内存 | 384 MiB | 在硬上限前更早触发垃圾回收，并为非堆内存留出余量 |
| 直接运行 Go 托管内存 | 512 MiB | 未显式设置 `GOMEMLIMIT` 时的进程默认保护线 |
| 交互查询并发 | 8 | 对所有远程数据源实施单节点全局背压 |
| 单次查询结果 | 16 MiB | 避免少量超大字段令进程内存突然增长 |
| 单个字段 | 1 MiB | 超出部分截断，并在结果元数据中标记原因 |
| 每个数据源连接池 | 8 个打开、4 个空闲 | 限制多数据源连接和后台资源占用 |
| 仪表盘卡片加载 | 最多 4 个并行请求 | 在首屏速度与浏览器、服务端压力之间取得平衡 |

查询仍保留 1,000 行默认上限。达到行数、结果字节数或字段字节数限制时，接口会在 `meta.truncated` 和 `meta.truncation_reason` 中明确标记；前端不能把截断结果误认为完整数据。

为防止错误配置本身造成内存分配事故，单节点查询并发和单数据源连接池最多可配置为 128，单次结果保护线上限为 256 MiB，单字段保护线上限为 16 MiB。需要处理更大的明细数据时，应通过筛选、聚合或数仓物化缩小交互结果，而不是继续放宽网页查询上限。

## 页面加载

文本、HTML、CSS、JavaScript 和 JSON 响应支持 gzip 流式压缩。图表运行库只在分析详情、仪表盘和公开嵌入页面加载，不进入首页与普通数据浏览首屏。

仪表盘在快速切换标签、修改筛选或刷新时会取消已经过期的请求。离开页面、重新渲染或移除卡片时会释放定时器、图表实例、监听器和隐藏标签的数据缓存，避免长时间使用后浏览器越来越卡。

## 监控

管理员监控接口 `/api/admin/monitor` 返回当前节点的：

- Go 堆已分配和正在使用的字节数；
- 向操作系统申请的总内存；
- 堆对象、GC 次数和 goroutine 数量；
- 当前生效的 Go 内存限制。

多节点部署要分别采集每个节点，并在负载均衡或监控平台设置内存、重启次数、请求延迟和数据库连接告警。只观察应用数据库不能发现 Topbase 节点本身的内存压力。

## 发布验收

每次整体功能升级至少执行：

1. 完整单元测试、竞态检测与静态检查；
2. 冷启动后记录空闲 RSS、goroutine 和堆使用量；
3. 对大字段、结果上限、并发等待和客户端取消进行回归；
4. 验证主要 JavaScript 资源启用 gzip，且压缩响应可以正确解码；
5. 对多卡片仪表盘反复切换标签和刷新，确认旧请求被取消、图表实例被释放；
6. 在目标容器内存下持续压测，确认不会发生 OOM 重启，并记录 P95/P99 延迟。

容量测试结果与机器配置、数据库响应速度、查询复杂度和用户并发有关。新增驱动、图表类型、导出方式或后台任务时，必须重新验证内存峰值，不能沿用旧结论。
